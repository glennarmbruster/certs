Exam domain · 20–25%

User identities

Cloud-only user

When to use it. A new employee has no on-premises directory account and needs an identity managed entirely in Entra.

A cloud-created user is administered in the tenant without inbound directory synchronization. Verify the usage location and group assignments before provisioning licensed services.

B2B collaboration invitation

When to use it. A partner developer must access a tenant application while continuing to authenticate with a home identity.

An invited B2B guest has a resource-tenant object linked to external authentication. Review redemption status and the identity provider used to accept the invitation.

Dynamic group membership

When to use it. Employee department attributes should automatically determine membership in an application access group.

A dynamic membership rule evaluates supported user or device attributes and updates group membership. Verify the exact source attribute and rule processing status when a user is missing.

Administrative units

When to use it. Regional help desk teams need directory administration confined to users in their own region.

A supported scoped directory role can be assigned against an administrative unit. Adding a group to the unit does not by itself put all its members directly in scope for user administration.

Cross-tenant synchronization

When to use it. Two business tenants want automated provisioning and lifecycle updates for collaborating users.

Cross-tenant synchronization provisions B2B collaboration users from a source to a target tenant. Check the provisioning scope, inbound permission and attribute mappings before diagnosing missing users.

Entra Connect Sync staging mode

When to use it. A standby synchronization server should import and synchronize data without exporting production changes.

Staging mode permits configuration checks and previews while suppressing normal exports. Coordinate failover so that only the intended server actively exports changes.

Password hash synchronization

When to use it. A company wants cloud authentication to continue when its on-premises sign-in agents are unavailable.

A derived hash of the on-premises password hash is synchronized for validation in the cloud. Check password hash synchronization health and allow for propagation after a password change.

Pass-through authentication

When to use it. Cloud sign-ins must be validated against on-premises AD through tenant-registered authentication agents.

Agents validate supplied credentials against Active Directory instead of using a cloud-side password verifier for that sign-in. Maintain multiple healthy agents and network connectivity to avoid a single dependency.

Source anchor matching

When to use it. A migrated directory user must continue linking to the same cloud identity across sync cycles.

A stable source anchor identifies the synchronized object independently of display name changes. Compare source anchor and cloud immutable identity carefully before any matching correction.

Synchronization scoping filter

When to use it. Users from a newly created organizational unit never appear in the tenant even after a successful sync.

Domain, OU or attribute scoping determines which source objects enter a synchronization flow. Review pending exports after changing scope because removing objects from scope can stage deletions.

Provisioning logs

When to use it. A SCIM-connected application is missing one user while other assigned users provision successfully.

Provisioning logs show per-object evaluation, mapping, target requests and error details. Filter by the specific user and cycle and inspect whether assignment or matching skipped the object.

Hybrid device join

When to use it. Company-owned Windows computers remain AD domain joined and must gain a corresponding Entra device identity.

Hybrid join registers a domain-joined device with the tenant for supported identity and access scenarios. Use dsregcmd /status to compare DomainJoined, AzureAdJoined and the expected tenant context.

Exam domain · 25–30%

Authentication and access management

Conditional Access report-only

When to use it. A proposed access policy should be evaluated against real sign-ins before it can interrupt users.

Report-only evaluation records the projected outcome while leaving the candidate policy unenforced. Inspect report-only results for successful, failed and user-action-required sign-ins.

Conditional Access What If

When to use it. A designer needs to predict which access policies a hypothetical user, application and location combination will match.

What If evaluates supplied conditions against configured policies. Specify relevant client, resource and device conditions and confirm with actual sign-in logs afterward.

Authentication strength

When to use it. An application requires phishing-resistant authentication and a general MFA claim alone is insufficient.

Authentication strengths restrict acceptable authentication method combinations for the targeted sign-in. Verify a matching method is registered and available before enforcing the strength.

Temporary Access Pass

When to use it. A new hire needs a time-limited bootstrap credential to register passwordless methods.

A Temporary Access Pass lets an eligible user authenticate during a defined onboarding window. Check issuance, lifetime and single-use settings when the onboarding credential fails.

Passkey authentication

When to use it. A security team wants a sign-in credential bound cryptographically to the legitimate relying party.

A passkey uses public-key authentication so the service verifies a signature against a registered public key. Plan for supported devices, registration and recovery if a user's authenticator is lost.

Self-service reset writeback

When to use it. An employee resets a synchronized password in the cloud and must immediately use that password in on-premises AD.

Password writeback sends supported cloud password changes back to the on-premises directory. Verify connector permissions and the on-premises password policy if a reset is rejected.

Sign-in log Conditional Access tab

When to use it. A user received a block page and the administrator needs the exact policy evaluation for that event.

The sign-in's policy details show which policies applied and their outcome. Match timestamp, user, resource and correlation ID before interpreting the event.

User risk remediation

When to use it. Risk detections indicate an account may be compromised across multiple sign-in events.

A user-risk policy can require supported remediation such as a secure password change. Verify the user can complete required MFA and password reset flows before depending on self-remediation.

Sign-in risk policy

When to use it. An organization wants additional verification when a particular authentication attempt is suspicious.

A risk-based Conditional Access decision can challenge the current sign-in based on its calculated risk. Compare risk at sign-in with later risk updates when reconciling reports.

Require compliant device

When to use it. A payroll app should admit managed devices only after they meet the organization's compliance policy.

Conditional Access uses the device compliance signal provided by a supported device management system. Inspect device identity, compliance state and the client’s ability to present its device identity.

Named locations

When to use it. A policy should distinguish connections from explicitly registered corporate egress IP ranges.

Named locations represent defined network locations for Conditional Access evaluation. Use the public egress address visible to the identity service when configuring IP ranges.

Emergency access account

When to use it. Administrators need a recovery path if normal authentication dependencies or policies lock them out.

An independently protected emergency account can restore control during identity outages or policy errors. Test access periodically and alert on every use of the emergency identity.

Session sign-in frequency

When to use it. A sensitive application requires users to reauthenticate at a defined interval.

A session control sets how long authentication can be reused before reauthentication is required. Evaluate client and token behavior when testing the next interactive challenge.

Authentication methods policy

When to use it. A tenant wants only a pilot group to register a newly enabled authentication method.

The authentication methods policy controls method availability and scope. Check the targeted group and method settings when a user cannot register the expected method.

Exam domain · 20–25%

Workload identities

Application registration

When to use it. A development team needs a client ID, redirect URI and declared permissions for its application.

An app registration defines an application object in its home tenant. Check the redirect URI matches the application's request exactly when authorization fails.

Enterprise application service principal

When to use it. An administrator needs to control a third-party application's access and sign-in assignments in the local tenant.

A service principal represents an application instance in a particular tenant. Use the local object ID for assignments rather than confusing it with the application client ID.

Delegated permission

When to use it. An interactive app should read information on behalf of the signed-in employee.

Delegated access combines the granted delegated permissions with the user's access rights. Inspect the scopes claim in a delegated access token when troubleshooting resource authorization.

Application permission

When to use it. A daemon must read permitted directory data with no signed-in user.

Application permissions authorize an application identity to act independently of a user. Review administrator consent and app roles and avoid granting unnecessary tenant-wide permissions.

User-assigned managed identity

When to use it. Several Azure resources need the same identity to access a shared dependency and its lifecycle must be independent of one VM.

A user-assigned managed identity is a separate resource that can be attached to supported hosts. Removing a host does not itself delete the identity or its existing access assignments.

Federated identity credential

When to use it. A build workload needs to exchange a trusted external identity token for an Entra token without a stored client secret.

Workload identity federation validates configured issuer, audience and subject claims. Compare the token subject exactly with the configured external workload identity.

Admin consent workflow

When to use it. An employee requests an application permission they cannot approve and the tenant needs a review queue.

The workflow submits consent requests to designated reviewers for evaluation. Review the publisher, permissions and business need before granting consent.

App role assignment

When to use it. An enterprise application defines Reader and Approver roles that should be assigned to different teams.

App role assignments associate principals with application-defined roles emitted in supported tokens. The application must interpret and enforce its role claims.

SCIM provisioning

When to use it. An enterprise SaaS application needs user accounts created, updated and deactivated based on assignments.

The provisioning service calls the target SCIM endpoint using attribute mappings and scoping rules. Test endpoint authorization and matching attributes before starting a broad provisioning cycle.

Application Proxy

When to use it. Remote staff need Entra preauthentication for a supported internal web app without publishing the app server directly.

A private network connector establishes outbound connectivity to the proxy service. Check connector health, internal URL reachability and the configured authentication method.

Workload identity sign-in logs

When to use it. An app-only background task fails authentication and no user interactive sign-in exists.

Service principal or managed identity sign-in logs record authentication for the corresponding workload identity type. Search by application or principal ID and time instead of filtering for an employee's UPN.

Identity governance

PIM eligible assignment

When to use it. A responder may activate a directory role during incidents but should have no standing active privilege.

Eligibility makes the role available for activation subject to the role's settings. Check eligibility dates, activation duration and approval requirements before an incident.

PIM role settings

When to use it. A privileged role must require justification, MFA and approval whenever eligible users activate it.

Role settings define activation controls for the particular role and resource scope. Review the settings for the target role because other roles may have different approval rules.

Recurring access review

When to use it. Guest membership in a legal collaboration group must be reapproved every quarter.

An access review schedules recurring decisions about whether access should continue. Define the reviewer, fallback outcome and whether results should be applied automatically.

Access package

When to use it. New project staff need a group, an application role and a SharePoint site assignment through a single request.

An access package bundles resource roles with policies for requesting and retaining access. Check each resource role in the package when an approved request grants only part of the expected access.

Entitlement management catalog

When to use it. Delegated business owners need to manage packages using an approved set of resources.

A catalog groups resources and access packages and supports delegated catalog administration. Add the required resource to the correct catalog before creating its package assignment.

Access package assignment policy

When to use it. External contractors may request project access only with sponsor approval and an expiry date.

An assignment policy defines eligible requestors, approval and assignment lifecycle for a package. Inspect the policy actually used by the request when access lasts longer than expected.

Connected organization

When to use it. Entitlement requests should be available to users from an identified partner organization.

A connected organization represents an external directory or domain that policies can reference. Verify associated domains and sponsors before opening a package to partner requestors.

Lifecycle Workflows

When to use it. A scheduled offboarding process should perform identity governance tasks based on employee lifecycle attributes.

Lifecycle Workflows orchestrate configured tasks for joiner, mover or leaver scenarios. Verify trigger attributes, timing and task execution history for the affected employee.

Terms of use

When to use it. An employee must acknowledge a specific published policy document when accessing a targeted application.

Entra terms of use can require acceptance through a Conditional Access grant control. Review the published document version and acceptance records when proving acknowledgement.

Directory audit logs

When to use it. An auditor needs evidence of who added a privileged directory role assignment and when.

Directory audit records capture supported changes to users, roles and other directory objects. Inspect the initiating actor, target resources and modified properties for the change.

PIM access review

When to use it. Governance staff must periodically verify whether eligible or active privileged role holders still need that assignment.

Privileged role reviews evaluate continuing need for designated role assignments. Scope the correct role and assignment type so standing active users are included when required.
